# 工业化制作与原型路线

[返回总览](README.md) · [设计总纲](00-framework.md) · [联动案例](02-system-interactions.md) · [版本边界](01-version-and-dlc.md)

本页将机制拆解转化为制作建议。**以下数据边界、工作流和测试方案是建议架构，不是 Paradox 内部实现的断言。** 这里的工业化指可持续生产、维护和验证大量相互作用的规则与内容，不意味着个人项目应提前搭建大型企业平台。

## 1. 按风险识别真正昂贵的部分

| 工作 | 难度来源 | 小型项目优先做什么 |
| --- | --- | --- |
| 继承与头衔 | 多条法律、多种资产与多人权利交接 | 少量头衔，确定性规则，清晰预览 |
| 人物关系 | 同一人物承担多种身份，信息有公开与秘密层 | 统一人物 ID，明确关系方向与知情者 |
| 政体扩展 | 多种制度修改共通规则 | 先完成一种制度，第二种只替换一条关键规则 |
| 内容生产 | 参与者选择、文本变化、历史与后果一致性 | 少量可复用模板，配套情境测试 |
| AI | 理解资格、比较价值、兼顾人格和性能 | 小规模、低频检查、可解释决策记录 |
| 界面 | 信息密度、关联导航、通知负担 | 原因拆解、人物关系和行动预览 |
| 地图与模拟 | 地点、道路、控制、军队与跨区域效果 | 小图和抽象移动，先验证决策 |
| 美术与本地化 | 大量人物身份、文化差异、文本变体 | 简单而统一的视觉语言，先保证可读性 |

CK3 的模组与补丁资料展示了可配置内容和规则扩展接口，但这不足以证明其内部所有逻辑都属于同一种架构。可以借鉴其公开的配置思路，具体项目仍应按规模选择。[^1]

## 2. 建议的数据边界

| 对象 | 自己保存什么 | 不应直接混入什么 |
| --- | --- | --- |
| Character | 身份、存活、年龄、人格、技能与个人资源 | 全世界关系的重复副本 |
| Relationship | 双方 ID、关系类型、方向、起止时间和事实来源 | 把婚姻、联盟、牵制合并为一个忠诚数值 |
| Secret | 事实、涉及人物、知情者、公开状态 | 默认向所有 AI 和界面公开 |
| Dynasty／House | 成员、领导者、共享资源、长期特性 | 所有成员的私人资产 |
| Title | 等级、持有人、法理关系、继承规则引用 | 将地图坐标、臣属和法理合并为一个父节点 |
| SubjectRelation | 主从双方、关系种类、契约 | 假定所有臣属都提供同一税率 |
| County／Holding | 地理、发展、控制、地产与建设 | 人物本身的继承资格 |
| OngoingAction | 发起者、目标、阶段、投入、风险与失效条件 | 静态规则定义的重复副本 |
| Situation | 范围、参与者、阶段、推动记录 | 把全部地区事件写死在一个巨大脚本里 |

原型可以使用很少的文件和普通数据结构实现这些边界。无需为了名字好看就引入 ECS、微服务、事件溯源数据库或复杂依赖框架。

## 3. 一个互动应有一致的规则契约

无论送礼、勒索、封赏还是招募，建议能回答同一组问题：

| 项目 | 需要明确的内容 |
| --- | --- |
| 可见条件 | 玩家什么时候应该知道存在这项行动 |
| 执行资格 | 当前谁能对谁做，失败原因是什么 |
| 支付条件 | 花什么、何时扣除、失败是否退回 |
| 接受与判定 | 对方是否同意，是否存在随机结果 |
| 实际效果 | 哪些人物、关系、权利、资源被改变 |
| 延迟效果 | 是否创建进行中的行动或后续故事 |
| 失效处理 | 目标死亡、职位变更、迁移、关系改变时怎样结束 |
| 信息解释 | 玩家可见什么，哪些内容必须仍然保密 |
| AI 评估 | 人格、利益、风险和制度条件如何进入考虑 |
| 记录与提示 | 让玩家知道发生了什么，为什么值得关注 |

界面预览与实际执行应调用同一套资格和效果计算。特别是[继承](modules/05-succession.md)、[战争和平](modules/18-war.md)与[契约](modules/10-subjects-factions.md)，不能各维护一份简化逻辑。

## 4. 内容生产流水线

1. **确定要制造的选择。** 先写“两个选项为什么都可能合理”，再写故事文本。
2. **定义参与者身份。** 例如“有宣称且不满的亲属”，并排除已死亡、重复或不可能出现的人物。
3. **读取已存在的世界事实。** 谁受过封赏、谁知道秘密、谁处在派系中。
4. **给选择配置真实后果。** 写回关系、资源或行动，而不只添加临时文本。
5. **提供状态相关文案。** 使用人物姓名、称谓、亲属关系和已经发生的事。
6. **处理替代路径。** 没有合格参与者时跳过或用合理替代，目标失效时收束故事。
7. **做少量情境验证。** 正常、资格不足、目标变化、多人重叠四类优先。
8. **检查重复和节奏。** 同一事件出现频率、同一人物曝光量以及每次打断带来的决策价值。

这是对事件、决议与故事机制的制作提炼。[22 模块](modules/22-events-stories.md)说明其设计作用，1.19 的故事界面提供了长期内容可视化的公开实例。[^2]

## 5. 调整平衡时观察什么

不要只统计平均收入和胜率，还要观察策略是否存在选择空间。

| 问题 | 可观察证据 | 可能的调整方向 |
| --- | --- | --- |
| 是否有支配性选项 | 不同人格、局面都选择同一选项 | 调整条件、机会成本或长期后果 |
| 压力是否影响玩法 | 玩家知道压力存在，却从不改变选择 | 让人格成本与实际风险相关 |
| 接班是否公平 | 玩家无法从预览预测权力变化 | 优先修复信息，再调惩罚 |
| 扩张是否有消化期 | 打下土地后立即无成本满额使用 | 通过控制、人事和整合任务表达成本 |
| 事件是否有意义 | 玩家记住弹窗但记不住人物 | 使用现存关系并保存后果 |
| AI 是否可信 | 行动符合数值但持续违背人格 | 分离利益评估与性格倾向，记录选择理由 |
| 通知是否过量 | 玩家机械关闭提示 | 合并重复信息，保留可操作的紧急问题 |
| 失败能否继续 | 一次危机后再无合理行动 | 提供退让、转移资产、改变身份等恢复路径 |

这些是建议观察项，不是 CK3 已公布的内部 KPI。先用小样本游玩找问题，避免编造“最佳通知频率”或“最佳选择比例”。

## 6. 推荐的第一个原型：小领主的继承危机

**要验证的问题：少量人物、关系和继承规则，能否在没有复杂战争与大地图时产生有意义的政治选择？**

| 项目 | 原型边界 |
| --- | --- |
| 世界 | 1 个小王国，6 个地区，约 12—20 名重要人物 |
| 玩家 | 一位即将面临接班的领主 |
| 人物 | 3 种人格，少量技能，1 条压力轨 |
| 家庭 | 2 名潜在继承人，少量婚姻候选 |
| 臣属 | 3—4 个封臣，2 种政治立场 |
| 资源 | 金币、政治资本、家族声望 |
| 行动 | 送礼、联姻、授地、调查秘密、勒索、任命 |
| 冲突 | 一个拥立派系；战争先用军队级简化结算 |
| 内容 | 约 10 个能读写现有关系的事件 |
| 必须完成 | 一次可预览的接班、一次反对派集结、至少两种处理路径 |
| 展示目标 | 一段可在约 20—30 分钟内体验完的闭环；这是设计目标，需实测调整 |

不要求第一版模拟真实中世纪人口，也不需要地图扩展、完整宗教编辑器、旅行、传奇和全套政体。可以使用原创架空背景，把精力放在关系和后果是否成立。

## 7. 按完成判据推进

| 阶段 | 做什么 | 完成判据 |
| --- | --- | --- |
| 规则纸面验证 | 人物、头衔、继承与派系表 | 能手算一场接班，所有权利归属明确 |
| 最小交互版 | 展示人物、发起互动、执行继承 | 预览与结果一致，关系和资源可追踪 |
| 可玩闭环 | 加入秘密、压力和少量事件 | 能走通妥协、结盟或冲突至少两种路线 |
| 垂直切片 | 改善界面、反馈、节奏和一套视觉 | 未读设计文档的人可以独立玩懂 |
| 单项扩展 | 只选行政任命、旅行或文化之一 | 新模块确实改变原有决策，且旧闭环仍成立 |

不提供未经团队能力、引擎熟悉度和质量目标校准的工期承诺。最大的前期风险是规则解释与连锁状态正确性，其次才是内容数量。

## 8. AI 辅助适合放在哪里

适合辅助：生成事件候选、整理规则表、编写清晰的资格检查、制作小范围测试用例、检查链接和术语一致性。产出必须经过实际规则和情境验证。

需要人工主导：核心体验目标、选择是否有趣、失败是否公平、角色与世界的价值表达，以及内容是否重复。模型可以提供不同方案，但不能凭一段漂亮文案证明玩法成立。

长期维护资产建议包括：模块职责表、规则变更记录、事件模板、重要情境样例与一份可运行原型。文档只在帮助实现和验证选择时才有价值。
